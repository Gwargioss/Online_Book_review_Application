-middleware: In Express, a middleware is a function that sits between the HTTP request and the HTTP response. 
Technically, a middleware is any function with the following signature:
(req, res, next) next → a function that passes control to the next middleware in the stack
Middleware functions are executed sequentially, in the exact order they are registered in the code
The Request–Response Lifecycle:
When an HTTP request hits an Express server:
1-Express creates req and res
2-The request enters the middleware stack
3-Each middleware decides one of three things:
  .Pass control → next()
  .End the request → res.send(), res.json(), etc.
  .Throw or pass an error → next(err)
If no middleware sends a response, the request hangs until timeout.

3️⃣ Middleware Stack Execution Model  https://expressjs.com/en/resources/middleware/
Express works like a stack / pipeline, not magic.
Example:
app.use(express.json())
app.use(logger)
app.use(auth)
app.use('/api', apiRoutes)

Execution order for a request to /api/users:
1-express.json()
2-logger
3-auth
4-apiRoutes
5-matching route handler
6-response is sent
7-stack stops
⚠️ Order is everything
Express does NOT reorder anything for you.

next() → goes to the next middleware
next(err) → skips all normal middleware, jumps directly to error-handling middleware.

5️⃣ How Does the Cycle Stop?
The request–response cycle logically ends when you send a response:
res.send()
res.json()
res.end()
res.redirect()

After this:
You SHOULD NOT call next()
Express will NOT automatically block you from doing it
If you do, you’ll get:
Error: Can't set headers after they are sent

6️⃣ Error-Handling Middleware (Special Case)
app.use((err, req, res, next) => {
  res.status(500).json({ message: err.message })
})
If you don’t define this → app crashes or leaks errors.

Common Mistakes (Interview Traps):
❌ “Everything in Express is middleware”
❌ Calling next() after res.send()
❌ Forgetting error middleware
❌ Wrong middleware order
❌ Assuming Express has defaults
❌ Parsing body after routes

One-Sentence Killer Summary (Use This)
Express handles requests using a middleware stack where each middleware function decides whether to pass control, end the response, or forward an error, and the entire flow depends strictly on registration order with no built-in defaults.

-What is the difference between JWT and session
1️⃣ Session-Based Authentication
How it works
User logs in.
Server verifies credentials.
Server creates a session object in memory or database.
Server sends back a session ID (usually in a cookie).
Every request:
Browser automatically sends the cookie.
Server looks up session ID in storage.
If found → user is authenticated.

Architecture
Client  --->  SessionID  --->  Server
                      (lookup in DB/memory)
Important properties
🔴 Stateful
Server must store session data.
🔴 Needs shared storage in distributed systems.
🔴 If server restarts and sessions are in memory → users logged out.
🟢 Easy to revoke (just delete session from DB).
🟢 Simple and secure when implemented correctly.

2️⃣ JWT (JSON Web Token)
How it works
User logs in.
Server verifies credentials.
Server creates a signed token containing user data.
Token is sent to client.
Every request:
Client sends token (usually in Authorization header).
Server verifies signature.
If valid → user authenticated.

Architecture
Client  --->  JWT Token  --->  Server
                (verify signature only)
Important properties

🟢 Stateless
Server stores NOTHING.
🟢 Scales easily across microservices.
🟢 No session store needed.
🔴 Hard to revoke (unless blacklist system exists).
🔴 Bigger attack surface if badly implemented.
🚨 Security Differences (This is where beginners mess up)
Session risks:
Session fixation
CSRF (if cookie-based)
Need HTTPS
Need secure cookie flags
JWT risks:
Storing in localStorage → XSS steals token
No expiration → permanent access
Using weak signing secret
Not validating algorithm properly
Putting sensitive data inside payload
-🎯 What "Stateless API" Means
Stateless =
Each request contains everything needed for authentication.
No server-side memory.
Session = breaks statelessness.
JWT = keeps statelessness.

-1️⃣ يعني إيه Starvation؟

Starvation =
Queue أو Phase عمرها ما ييجي دورها
مش عشان مفيش وقت
لكن عشان Queue تانية بتاكل كل الأولوية
Node شغال
Process شغال
لكن:
timers مش بتتنفذ
I/O مش بيتخدم
requests بتtimeout
يعني ميت منطقيًا

2️⃣ النوع الأول: process.nextTick Starvation (الأخطر)
ليه؟
لأن:
nextTick أعلى أولوية من أي حاجة
بيتنفذ بعد كل function
ويتفرّغ بالكامل
مثال قاتل:
function bomb() {
  process.nextTick(bomb);
}
bomb();

اللي بيحصل:
Call Stack يفضى
Event Loop:
يشوف nextTick queue → مش فاضية
ينفذ bomb
bomb يحط nextTick جديد
repeat للأبد
❌
timers مش بتتنفذ
fs callbacks مش بترجع
server مش بيرد
⚠️ CPU 100%
⚠️ Memory بيزيد
⚠️ No crash → أسوأ

3️⃣ النوع التاني: Microtask Starvation (Promises)
أخف شوية
بس خطر برضه
مثال:
function loop() {
  Promise.resolve().then(loop);
}
loop();

اللي بيحصل:
كل promise:
تتحط في Microtask Queue
Event Loop:
يفضّي المايكروتاسك بالكامل
مفيش فرصة لـ timers أو I/O
الفرق؟
process.nextTick أخطر
microtasks أبطأ شوية

  }
